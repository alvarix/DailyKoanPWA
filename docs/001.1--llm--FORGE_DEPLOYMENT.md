# Postmortem: Nginx Failure on Forge Droplet (DailyKoan Deployment)

## Executive Summary

On 2026-10-24, nginx crashed on the droplet `alfaForge` and remained down for three days. The root cause was a **syntax error in `/etc/nginx/forge-conf/3430825/site.conf`**: a full `server { }` block was pasted into a file that nginx includes **inside** an existing `server { }` context. Nginx validates all configuration files atomically; any syntax error anywhere causes the master process to refuse to start or reload, which brought down **every site on the droplet**, including the mission-critical client site (`wana....org`).

The prior session asserted that nginx changes in Forge's "Edit NGINX Settings" UI would be "sandboxed to that site." That assertion was false. Per-site *files* are isolated, but nginx's *failure domain* is not: one invalid `site.conf` poisons the entire `nginx -t` validation, which in turn poisons `systemctl start nginx`.

## (A) Postmortem — What Happened and Why

### Mechanism of the Crash

Forge's nginx architecture (evidenced from the wmw config, forge-conf id `3081769`) works like this:

1. `/etc/nginx/sites-available/{domain}` is the **wrapper**. It contains the `server { }` block, `listen` directives, `server_name`, and an `include forge-conf/{id}/site.conf;` or similar include of the per-site fragment.
2. `/etc/nginx/forge-conf/{id}/site.conf` is the **fragment**. The Forge UI "Edit NGINX Settings" edits **this fragment only**. It must contain directives legal inside a `server { }` block (e.g., `ssl_protocols`, `location /`, `access_log`). It must **not** contain `server {`, `listen`, `server_name`, or a closing `}` — those belong in the wrapper.
3. The prior session's doc (`docs/001--llm--FORGE_DEPLOYMENT.md`) presented a **full `server { }` block** and instructed: "The final config should look like this." The user pasted that full block into Forge's fragment editor. The file then contained:

```nginx
server {           # <-- ILLEGAL: nested server{} inside server{}
    listen 80;
    ...
```

4. On the next nginx reload/restart (triggered by a reboot or by Forge's own automation), `nginx -t` failed with:

```
"server" directive is not allowed here in /etc/nginx/forge-conf/3430825/site.conf:1
```

5. Because `nginx -t` failed, systemd refused to start nginx. **All sites** (not just DailyKoan) were unreachable.

### Why the "Sandboxed" Guarantee Was False

The assertion "NGINX changes were sandboxed to that site" conflated two things:

| What IS isolated | What is NOT isolated |
|---|---|
| Per-site file paths | Nginx's configuration validation (atomic, all-or-nothing) |
| `server_name` matching | The nginx master process refusing to start if ANY file is invalid |
| SSL certs per site | `systemctl start nginx` failing for the entire droplet |

Nginx does not have per-site process isolation in this setup. One `site.conf` with bad syntax makes `nginx -t` return non-zero, and `systemctl start nginx` exits with `1/FAILURE`. The failure domain is the **entire droplet**.

### Unknowns (Flagged, Not Assumed)

- **Did Forge validate before saving on Oct 24?** Forge may or may not run `nginx -t` before writing the file. The fact that the file was written with invalid syntax suggests either (a) Forge did not validate, or (b) validation was bypassed. We do not know which.
- **Will later Forge actions regenerate `site.conf`?** If you change the site's PHP version, add an SSL cert, or trigger a deployment hook, Forge may rewrite `site.conf` from its template. The corrected fragment in this doc should survive a *template-based* rewrite only if the template itself is updated (see Section C, Step 7).
- **Is the `/etc/nginx/sites-available/dailykoan.on-forge.com` wrapper intact?** We know it was backed up. We have not verified its current contents on the server.
- **Does `koan.alvarsirlin.dev` resolve to the droplet?** DNS must be verified before testing.

### The Missing Safety Gate

The one check that would have prevented the outage: **`sudo nginx -t` before any reload or restart.** The prior doc said "Click Update — Forge will validate and reload nginx automatically." That was treated as sufficient. It was not. An explicit, manual `nginx -t` run by the operator — before leaving the terminal — would have caught the nested `server {}` error immediately and allowed safe rollback.

---

## (B) Hard Safety Rules — Non-Negotiable

Apply these to **every** nginx operation on this droplet.

1. **Never leave unvalidated nginx config on disk.** After writing any config file, run `sudo nginx -t` before doing anything else.
2. **Reload, never restart.** Use `sudo systemctl reload nginx` (or `sudo nginx -s reload`). Restart is only for when nginx is already stopped.
3. **Baseline the client site before and after.** `curl -sSI https://wana....org` must return `200 OK` both before and after any nginx change.
4. **Never restore the `.bak` verbatim.** `~/nginx-backup/site.conf.bak` contains the nested `server {}` that caused the crash. Do not `cp` it back. Use it only as a forensic reference.
5. **Test on the server, not in the UI.** Forge's UI is an editor, not a validation gate. The server is the source of truth.
6. **When asked about safety, admit unknowns.** If a claim cannot be verified from server state or first-party documentation, flag it as an unknown risk. Do not assert it as truth.

### Step 2: Fresh Backup of the Empty File

```bash
sudo cp /etc/nginx/forge-conf/3430825/site.conf ~/nginx-backup/site.conf.empty-2026-10-29
```

### Step 3: Write the Corrected Body-Only Fragment

This fragment contains **only directives legal inside a `server { }` block**. It must NOT contain `server {`, `listen`, `server_name`, or a closing `}`.

```bash
sudo tee /etc/nginx/forge-conf/3430825/site.conf <<'FRAGMENT'
# DailyKoan — body-only fragment for Forge-managed site (id 3430825)
# DO NOT wrap this in server{} — Forge provides the wrapper.

ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:ECDHE-ECDSA-CHACHA20-POLY1305:ECDHE-RSA-CHACHA20-POLY1305:DHE-RSA-AES128-GCM-SHA256:DHE-RSA-AES256-GCM-SHA384;
ssl_prefer_server_ciphers off;
ssl_dhparam /etc/nginx/dhparams.pem;

add_header X-Frame-Options "SAMEORIGIN";
add_header X-XSS-Protection "1; mode=block";
add_header X-Content-Type-Options "nosniff";

index index.html index.htm;
charset utf-8;

# FORGE CONFIG (DO NOT REMOVE!)
# Forge may inject SSL and other directives via this include.
include forge-conf/3430825/server/*;

# Static assets served directly by nginx
location /static {
    alias /home/forge/dailykoan.on-forge.com/current/static;
    expires 30d;
    access_log off;
}

# PWA manifest and service worker
location = /manifest.json {
    alias /home/forge/dailykoan.on-forge.com/current/static/manifest.json;
}

location = /sw.js {
    alias /home/forge/dailykoan.on-forge.com/current/static/sw.js;
}

# All other requests → Gunicorn
location / {
    proxy_pass http://127.0.0.1:8001;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

location = /favicon.ico { access_log off; log_not_found off; }
location = /favicon.svg { access_log off; log_not_found off; }
location = /robots.txt  { access_log off; log_not_found off; }

access_log off;
error_log  /var/log/nginx/3430825-error.log error;

location ~ /\.(?!well-known).* {
    deny all;
}
FRAGMENT
```

> **Path discrepancy flagged:** The prior doc (`001--llm--FORGE_DEPLOYMENT.md`) used `/opt/dailykoan/static`. The checklist (`001--usr--forge-deploy-checklist.md`) says Forge auto-cloned to `~/dailykoan.on-forge.com/current/`. The fragment above uses the checklist path. **Verify on the server** that `/home/forge/dailykoan.on-forge.com/current/static/` exists before reloading. If the app is actually at `/opt/dailykoan/`, edit the alias paths before Step 5.

### Step 4: Validate Before You Breathe

```bash
sudo nginx -t
```

**If this fails:** immediately restore the empty safe state, then stop and investigate.

```bash
sudo cp ~/nginx-backup/site.conf.empty-2026-10-29 /etc/nginx/forge-conf/3430825/site.conf
sudo nginx -t
# Confirm "syntax is ok" again, then STOP. Do not reload.
```

**Only proceed if `nginx -t` returns success.**

### Step 5: Reload Nginx (Not Restart)

```bash
sudo systemctl reload nginx
```

This sends a signal to the running nginx master process. If the new config is valid, workers rotate gracefully. If it were invalid (it shouldn't be — you just validated), the old workers keep serving. This is why reload is safer than restart.

### Step 6: Verify Both Sites

```bash
# 6a. Client site must be unchanged
curl -sSI https://wana....org | head -1

# 6b. DK site should respond (likely 502 Bad Gateway until gunicorn is running)
curl -sSI https://koan.alvarsirlin.dev | head -1

# 6c. Check nginx error log for any unexpected warnings
sudo tail -n 20 /var/log/nginx/3430825-error.log
```

A `502` from DK is expected at this stage — it means nginx accepted the config, parsed the `location /` proxy, and reached the upstream, but nothing is listening on `127.0.0.1:8001` yet. That is correct. A `404` or `500` from nginx itself would be wrong.

### Step 7: Document What You Did

On the server, in `~/nginx-backup/` or similar, create a note:

```bash
cat > ~/nginx-backup/RESTORE-NOTE-2026-10-29.txt <<'EOF'
Restored DK site.conf with body-only fragment.
Used path: /home/forge/dailykoan.on-forge.com/current/static
Verified nginx -t passed before reload.
Client site wana....org confirmed 200 after reload.
EOF
```

## For Dummies (Plain English)

**What went wrong:** The previous instructions showed a full nginx config block and said "paste this." But the place where you paste it (Forge's website editor) only accepts the *inside* of that block, not the wrapper. So a `server { }` got nested inside another `server { }`, which nginx hates. Nginx checks all files at once; one bad file = whole server won't start. Your client's site went down for 3 days.

**How we stop it:** Every time we touch nginx, we run `sudo nginx -t` *before* reloading. If it says anything other than "syntax is ok," we undo our change and stop. We also check the client site with `curl` before and after, to make sure it still works.

**What we're doing now:** We're writing a *fragment* (just the inside, no wrapper) for the DailyKoan site. Then we validate, reload gently (not restart), and verify both sites still respond.

**What we still don't know:** We don't know if Forge will ever overwrite this file again from its template. We don't know if the app is actually in `/opt/dailykoan` or `~/dailykoan.on-forge.com/current/`. These are flagged as "check on the server first."
