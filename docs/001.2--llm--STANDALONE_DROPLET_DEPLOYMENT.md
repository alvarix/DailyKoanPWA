# Daily Koan PWA — Standalone Droplet Deployment (Doc 001.2)

Version: 001.2 — llm
Status: DRAFT — not yet executed. Checkboxes for execution live in `docs/001.3--usr--standalone-droplet-checklist.md`.

## Purpose

Deploy Daily Koan on a **brand-new, separate DigitalOcean droplet**, fully isolated from the Forge-managed `alfaForge` droplet.

Why a separate droplet: on 2026-10-24 a bad nginx fragment took nginx down on `alfaForge` for 3 days and took the client site (`wana....org`) with it. Nginx's validation is atomic across the whole droplet — one syntax error anywhere and the master process refuses to start. The only real isolation is a separate machine. On a dedicated droplet, the **failure domain is this app and nothing else**. A mistake here costs you a koan, not a client.

This doc is standalone-safe: every command runs on the new droplet (`<STANDALONE_IP>`). **Nothing in this procedure logs into `alfaForge`.**

```
                  +---------------------------+
                  | alfaForge (Forge-managed) |   client site, wmw
                  |  DO NOT TOUCH             |   (untouched by this doc)
                  +---------------------------+

                  +---------------------------+
  dailykoan.duckdns.org  -->                    |   dkStandalone (this doc)
                  |  nginx -> gunicorn :8001  |
                  |  /opt/dailykoan           |
                  +---------------------------+
```

## Phase 2 — First-Login Hardening

**Plain English:** the droplet currently has only `root`, and SSH accepts passwords. This phase: (1) create your personal user `alvar` plus a faceless `koan` account that will run the app, (2) prove your key and password work, (3) switch SSH to key-only, (4) switch on a firewall that only allows SSH and web traffic, (5) turn on automatic security updates.

### Shell legend — every code block in this doc is labeled

| Label | What it is | How to open | When you can close it |
| --- | --- | --- | --- |
| `LAPTOP#` | a plain terminal on your Mac, not SSH'd anywhere | open Terminal | whenever; re-open fresh for each gate |
| `ROOT#` | SSH session as root on the droplet | `ssh root@<STANDALONE_IP>` | end of Phase 2, once the 2.2 gates pass — afterwards it is only an emergency hatch |
| `ALVAR#` | SSH session as alvar on the droplet | `ssh alvar@<STANDALONE_IP>` | whenever; this is your daily driver from Phase 3 on |

Rules of thumb:

- **Gates run from `LAPTOP#`** — a gate must prove the outside world reaches the box the way a real visitor would.
- **Setup commands run in `ROOT#` or `ALVAR#`** — everything is sudo-prefixed and works in either.
- Nothing in this doc kills your open shells; a daemon reload only makes it re-read config.
- Keep `ROOT#` open until the 2.2 gates pass, then you may close it for good.

**2.0 Open the shells you will need**

Shell: `LAPTOP#` — open a terminal, keep it for the gates.

Shell: `ROOT#`:

```bash
ssh root@<STANDALONE_IP>
```

**2.1 Create a sudo user and a service user**

Plain English: two accounts. `alvar` is you — owns deploys, can sudo with its password. `koan` is a faceless system account that will run the app — it cannot log in, and it owns the app files.

Shell: `ROOT#`

```bash
adduser alvar            # set a strong password; used ONLY for sudo — SSH logins become key-only in 2.2
usermod -aG sudo alvar
mkdir -p /home/alvar/.ssh && cp ~/.ssh/authorized_keys /home/alvar/.ssh/
chown -R alvar:alvar /home/alvar/.ssh && chmod 700 /home/alvar/.ssh && chmod 600 /home/alvar/.ssh/authorized_keys

useradd -r -s /bin/false koan   # system user that runs the app; no password, no login
```

GATE — Shell: `LAPTOP#`, a fresh terminal (NOT the root session). Proves alvar's key AND password work BEFORE password login is removed:

```bash
ssh -t alvar@<STANDALONE_IP> 'sudo -v && echo SUDO_OK'
# Prompts for ALVAR's own password (set during adduser), then prints SUDO_OK.
```

> Gate correction (2026-11-15): the original `sudo -n true` could never pass — `-n` means
> fail-instead-of-prompt, and stock Ubuntu sudoers (%sudo ALL=(ALL:ALL) ALL) requires a
> password; NOPASSWD is not default. `ssh -t` allocates the TTY sudo needs to prompt. If the
> password is rejected, it was never set: as root run `passwd alvar` and retry. Disabling SSH
> password authentication below does not affect this local sudo prompt.

**2.2 Disable password SSH**

Plain English: writes a small sshd drop-in that refuses password logins, syntax-checks sshd, and gently reloads it. From now on the only way in is an SSH key — for everyone, including root.

Shell: `ROOT#` (or `ALVAR#` — sudo prompts once for alvar's password)

```bash
# Ubuntu 24.04 cloud images may force PasswordAuthentication via a drop-in.
printf 'PasswordAuthentication no\nKbdInteractiveAuthentication no\n' | sudo tee /etc/ssh/sshd_config.d/99-hardening.conf
sudo sshd -t          # GATE: must print nothing (syntax ok)
sudo systemctl reload ssh
```

GATES — Shell: `LAPTOP#`, fresh commands:

```bash
ssh alvar@<STANDALONE_IP> 'echo KEY_OK'                # Expect: KEY_OK, no password asked
ssh -o PubkeyAuthentication=no alvar@<STANDALONE_IP>   # Expect: "Permission denied (publickey)" — FAILING IS PASSING
```

If the first asks for a password, or the second lets you in with one, password auth is still live — fix before moving on. (Undo from `ROOT#`: `rm /etc/ssh/sshd_config.d/99-hardening.conf && systemctl reload ssh`.)

**You may now close `ROOT#`** — alvar's key and sudo are proven, so root is only an emergency hatch from here on.

**2.3 Firewall — allow BEFORE enable**

Plain English: opens the only three doors this box needs (SSH, web 80, web 443) FIRST, then switches the firewall on — allow-before-enable so you never lock yourself out. `enable` also makes it survive reboots.

Shell: `ROOT#` or `ALVAR#`

```bash
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable        # answer y to "Proceed with operation (y|n)?"
sudo ufw status        # GATE: "Status: active" + all three rules listed
```

**2.4 Unattended security updates**

Plain English: makes Ubuntu install its own security patches daily, so the box does not depend on you remembering.

Shell: `ROOT#` or `ALVAR#`

```bash
sudo apt update && sudo apt install -y unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades   # choose "Yes"
```

**End of Phase 2.** From Phase 3 on, everything runs in `ROOT#` or `ALVAR#` unless a block says otherwise.

## Phase 3 — Packages and Code
**Plain English:** install the toolchain, put the code on the box, and build the private Python environment plus the generated assets (keys, database, icons). Everything in this phase runs on the droplet.

**3.1 Packages**
Plain English: installs the web server (nginx), the certificate bot (certbot), Python venv tooling, git, and the sqlite3 CLI (needed for the safe backups in Phase 9).

Shell: `ROOT#` or `ALVAR#`:

```bash
sudo apt install -y nginx certbot python3-certbot-nginx python3-venv python3-pip git sqlite3
```

(`sqlite3` CLI is needed for the safe backup procedure in Phase 9.)

**3.2 Code**

Option A — GitHub:

Plain English: downloads the app into /opt/dailykoan, owned by the koan user.

Shell: `ROOT#` or `ALVAR#`:

```bash
sudo mkdir -p /opt/dailykoan
sudo chown -R koan:koan /opt/dailykoan
sudo -u koan git clone https://github.com/<USER>/DailyKoanPWA.git /opt/dailykoan
```

> **Pulling later as alvar?** (2026-11-15, hit live) The repo is owned by `koan` (cloned as koan),
> so git >= 2.35.1 refuses `git pull` as a different user: `fatal: detected dubious ownership`.
> Pull as the owner - `sudo -u koan git pull` - which is what the Phase 9.2 update procedure
> uses anyway. (Or, as alvar once: `git config --global --add safe.directory /opt/dailykoan`.)


Option B — rsync from laptop (run from `/Users/alvarsirlin/Sites/apps/DailyKoanPWA`):

Plain English: pushes the code from your Mac instead, skipping the private stuff (venv, git, local test DB, keys) — the droplet generates its own next.

Shell: `LAPTOP#` for the rsync (run from your project folder); then `ROOT#` for the sudo rsync line in the comment:

```bash
rsync -avz --exclude=venv --exclude=.git --exclude=subscriptions.db --exclude='*.pem' --exclude='*.db' ./ alvar@<STANDALONE_IP>:/tmp/dailykoan/
# then on the droplet: sudo rsync -a /tmp/dailykoan/ /opt/dailykoan/ && sudo chown -R koan:koan /opt/dailykoan
```

The excludes matter: local test data (`subscriptions.db`, VAPID `.pem` from ngrok testing) must not ship to production. The droplet generates its own in Phase 3.3.

**3.3 Environment and generated assets**

Plain English: builds the app's private Python environment and generates its three machine-local assets — the VAPID key pair (signs push notifications), the empty subscriptions database, and the PWA icons.

Shell: `ROOT#` (the `sudo -u koan` runs each step as the app user):

```bash
cd /opt/dailykoan
sudo -u koan python3 -m venv venv
sudo -u koan venv/bin/pip install -r requirements.txt
sudo -u koan venv/bin/python init_vapid.py   # fresh keys — fine at launch (see Unknowns)
sudo -u koan venv/bin/python init_db.py
sudo -u koan venv/bin/python init_icons.py
sudo chmod 600 /opt/dailykoan/vapid_private.pem
```

> **If `init_vapid.py` fails with `TypeError: curve must be an EllipticCurve instance`:**
> (2026-11-15, hit live) the `py-vapid` pin in `requirements.txt` (1.9.2) predates modern
> `cryptography` (50.x, unpinned/transitive) - the old pin passes the curve class where the
> new library requires an instance. Fix on the droplet: `sudo -u koan venv/bin/pip install -U py-vapid`
> (1.9.4+ needed; 1.9.6 current), rerun. `requirements.txt` now pins the tested pair
> (py-vapid==1.9.6, cryptography==50.0.2). Same pattern applies if `pywebpush` (2.0.3) misbehaves
> on the daily-push gate: bump to the local known-good (pywebpush==2.1.2).


GATE:

Shell: `ROOT#` or `ALVAR#` (on the droplet):

```bash
sudo ls -l /opt/dailykoan/vapid_private.pem /opt/dailykoan/subscriptions.db /opt/dailykoan/static/icon-192.png
# All three must exist.
```

## Phase 4 — Gunicorn Service
**Plain English:** registers the app with systemd so gunicorn starts now, at every boot, and after crashes. The unit file is a job description for the OS — who runs it, from where, with which settings.

`/etc/systemd/system/dailykoan.service` (create with sudo):

Shell: `ROOT#` or `ALVAR#` — e.g. `sudo vim /etc/systemd/system/dailykoan.service`, then paste:

```ini
[Unit]
Description=Daily Koan PWA
After=network.target

[Service]
User=koan
Group=koan
WorkingDirectory=/opt/dailykoan
Environment="PATH=/opt/dailykoan/venv/bin"
Environment="FLASK_HOST=127.0.0.1"
Environment="FLASK_DEBUG=0"
Environment="BASE_URL=https://dailykoan.duckdns.org/"
ExecStart=/opt/dailykoan/venv/bin/gunicorn app:app -b 127.0.0.1:8001 --workers 1 --timeout 30
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

Note: unit output (stdout/stderr) goes to the systemd journal by default — that is what `journalctl -u dailykoan` reads.

Shell: `ROOT#` or `ALVAR#`:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now dailykoan
```

GATE:

Shell: `ROOT#` or `ALVAR#` — 127.0.0.1 is the droplet itself, so this runs ON the droplet:

```bash
curl -s http://127.0.0.1:8001/api/today | head -c 120
# Expect: JSON with today's koan. If empty, check: journalctl -u dailykoan -n 50
```

## Phase 5 — DNS (DuckDNS)
**Plain English:** points the public name at this droplet so browsers and iPhones can find it. The DuckDNS call can run from anywhere; run the dig gate from your laptop.

No custom domain is owned yet, so the app runs on a free DuckDNS subdomain: `dailykoan.duckdns.org`.

1. Create a free account at duckdns.org (GitHub login works)
2. Create the subdomain `dailykoan`
3. Point it at the droplet — web panel, or the update API:

Shell: `LAPTOP#` (or anywhere — it just tells DuckDNS the droplet IP):

```bash
curl "https://www.duckdns.org/update?domains=dailykoan&token=<DUCKDNS_TOKEN>&ip=<STANDALONE_IP>"
# Expect: OK
```

GATE (usually instant):

Shell: `LAPTOP#`:

```bash
dig +short dailykoan.duckdns.org
# Expect: <STANDALONE_IP>
```

Only proceed to Phase 6 once dig returns the droplet IP — Let's Encrypt validates against live DNS, and running certbot early just burns failed-issuence attempts.

TTL is short and fixed by DuckDNS (not configurable) — propagation is minutes, and the Doc 001.11 cutover needs no TTL games.

## Phase 6 — nginx
**Plain English:** nginx is the front door — it answers the public URL, serves static files itself, and hands everything else to gunicorn. Write the config, link it live, syntax-check, gently reload.

This droplet has no Forge, so here we write a **full `server { }` block** — the normal, non-Forge way. (The body-only-fragment rule from `001.1` applies only to Forge-managed sites.)

`/etc/nginx/sites-available/koan`:

Shell: `ROOT#` or `ALVAR#` — `sudo vim /etc/nginx/sites-available/koan`, then paste:

```nginx
server {
    listen 80;
    listen [::]:80;
    server_name dailykoan.duckdns.org;

    # Static assets served directly by nginx
    location /static {
        alias /opt/dailykoan/static;
        expires 30d;
        access_log off;
    }

    # PWA manifest and service worker (Flask also routes these; nginx serves them directly)
    location = /manifest.json { alias /opt/dailykoan/static/manifest.json; }
    location = /sw.js          { alias /opt/dailykoan/static/sw.js; }

    # Everything else -> gunicorn
    location / {
        proxy_pass http://127.0.0.1:8001;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location = /favicon.ico { access_log off; log_not_found off; }
    location = /favicon.svg { access_log off; log_not_found off; }
    location = /robots.txt  { access_log off; log_not_found off; }
}
```

Enable and validate:

Shell: `ROOT#` or `ALVAR#`:

```bash
sudo ln -s /etc/nginx/sites-available/koan /etc/nginx/sites-enabled/
sudo nginx -t                 # GATE: "syntax is ok" — non-negotiable, same rule as on Forge
sudo systemctl reload nginx   # reload, never restart, while nginx is up
```

GATE:

Shell: `LAPTOP#` — this checks the public path (DNS -> nginx -> gunicorn):

```bash
curl -sI http://dailykoan.duckdns.org/api/today | head -1
# Expect: HTTP/1.1 200
```

## Phase 7 — HTTPS
**Plain English:** certbot asks Let's Encrypt for a certificate, proves we control the name, then edits our nginx file to add HTTPS and an HTTP-to-HTTPS redirect. We re-validate afterwards, because certbot just edited our config.

Shell: `ROOT#` or `ALVAR#`:

```bash
sudo certbot --nginx -d dailykoan.duckdns.org
```

Certbot edits the block above to add 443 + an HTTP→HTTPS redirect.

GATES:

Shell: `ROOT#` or `ALVAR#` (the https curl can also run from `LAPTOP#`):

```bash
sudo nginx -t                        # certbot just edited the config — re-validate
sudo systemctl reload nginx
curl -sI https://dailykoan.duckdns.org/api/today | head -1   # Expect: 200
sudo certbot renew --dry-run                                  # Expect: success (auto-renewal works)
```

## Phase 8 — Daily Push Timer
**Plain English:** an alarm clock. At 08:00 UTC systemd runs `push_sender.py` once, which sends today's koan to every subscriber. The .service file is the job, the .timer file is the schedule.

Shell: `ROOT#` or `ALVAR#` — create both unit files with sudo vim, then run the enable block:

`/etc/systemd/system/dailykoan-push.service`:

```ini
[Unit]
Description=Daily Koan Push Sender

[Service]
Type=oneshot
User=koan
WorkingDirectory=/opt/dailykoan
Environment="PATH=/opt/dailykoan/venv/bin"
Environment="BASE_URL=https://dailykoan.duckdns.org/"
ExecStart=/opt/dailykoan/venv/bin/python push_sender.py
```

`/etc/systemd/system/dailykoan-push.timer`:

```ini
[Unit]
Description=Daily Koan Push Timer

[Timer]
OnCalendar=*-*-* 08:00:00
Persistent=true

[Install]
WantedBy=timers.target
```

`Persistent=true` means: if the box was down at 08:00, the missed run fires at next boot. `push_sender.py` always sends *today's* koan at run time, so a catch-up run just re-sends today's koan — a harmless duplicate. Set `Persistent=false` if you would rather skip missed days.

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now dailykoan-push.timer
systemctl list-timers dailykoan-push.timer   # GATE: shows the NEXT scheduled run
```

GATE (manual test run — with zero subscribers it should print "Sending to 0 subscription(s)..."):

```bash
sudo systemctl start dailykoan-push.service
sudo journalctl -u dailykoan-push.service -n 20 --no-pager   # push output runs as koan - alvar needs sudo to read its journal
```

## Phase 9 — End-to-End Test and Maintenance

**9.1 iOS end-to-end**

Plain English: the real test, on your iPhone. This is the whole point of the app — and it only works over HTTPS from a real name, which you now have.

1. Open `https://dailykoan.duckdns.org` in Safari (iOS 16.4+)
2. Share → Add to Home Screen → open from Home Screen
3. Tap the bell → allow notifications
4. GATE: `curl -s https://dailykoan.duckdns.org/api/subscriptions/count` → count includes your device
5. GATE: `sudo systemctl start dailykoan-push.service` → notification arrives; tapping it opens the right koan page

**9.2 Update procedure (after code changes)**

Plain English: how to ship code changes later — pull and restart.

Shell: `LAPTOP#` — the whole thing is one ssh one-liner from your Mac:

```bash
ssh alvar@<STANDALONE_IP> 'cd /opt/dailykoan && sudo -u koan git pull && sudo systemctl restart dailykoan'
```

**9.3 Safe backups — never `cp` a live SQLite file**

Plain English: copies of the two irreplaceable things — the push keys and the subscriber list — taken safely while the app keeps running.

Shell: `ROOT#` or `ALVAR#`:

The SQLite CLI `.backup` command takes a consistent snapshot even while gunicorn is writing:

```bash
sudo -u koan sqlite3 /opt/dailykoan/subscriptions.db ".backup '/opt/dailykoan/subscriptions-backup-$(date +%F).db'"
sudo cp /opt/dailykoan/vapid_private.pem /opt/dailykoan/vapid_public.pem /root/koan-key-backup/
```

**The VAPID key pair is the irreplaceable state.** The DB can be rebuilt from re-subscriptions; the keys cannot be regenerated without invalidating every subscriber. Store a copy somewhere off the droplet (password manager, encrypted disk).

**9.4 Logs / health**

Plain English: where to look when something misbehaves.

Shell: `ROOT#` or `ALVAR#` — journalctl for other users' units needs sudo:

```bash
journalctl -u dailykoan -f                       # app log
sudo journalctl -u dailykoan-push.service -n 50       # push results ("Sent: N, Removed dead: M")
curl -s https://dailykoan.duckdns.org/api/today   # health check
```

## For Dummies (Plain English)

We are renting a second small server ($6/mo) that does one job: serve the koan app. Your other server — the one with the client site — is never logged into during this whole procedure, so nothing you do here can break it. The new server gets: the code, two encryption keys (for notifications), a tiny database (who wants notifications), a web server in front (nginx), a padlock (HTTPS), and an alarm clock (the 08:00 timer). Each step ends with a check ("GATE") — if the check fails, you stop and fix; you never continue on top of a broken step. The two keys are the crown jewels: copy them somewhere safe, because if you lose them, everyone who subscribed must re-subscribe.
